# Job workspaces

Every job-description tool saves one private workspace before generating. Paste a nonblank posting (up to 15,000 characters / 60,000 UTF-8 bytes), or reopen an existing job. Identical normalized postings reopen the owner's existing workspace; matching titles alone do not merge opportunities. Tools can run in any order, including résumé tailoring first. Use Revise or Start over to improve output in the same workspace.

## Server storage and authorization

Session cookies are verified with revocation checking. The resulting UID and owner role (`terrell`) scope every repository operation. Client UID fields and headers cannot establish ownership. All mutations require same-origin requests; private responses use `private, no-store` and `Vary: Cookie`.

Live storage requires explicit server configuration:

```
JOB_WORKSPACE_MODE=live
JOB_WORKSPACE_DATABASE=<designated Firestore database ID>
JOB_WORKSPACE_BUCKET=<designated private bucket name>
```

Use the normal Firebase Functions runtime identity with existing designated resources. No custom IAM role setup is part of this feature. The checked-in `firestore.rules` and `storage.rules` deny direct client access; all private data goes through owner-authorized Functions. Firebase Admin bypasses client rules, so route authorization remains mandatory. Rules apply in production when deployed as well as in the emulators. Do not issue download tokens or put service credentials in browser configuration. Normal deployment smoke checks verify the runtime can use its configured resources; local work requires no cloud permissions or credentials. [Firebase explains the server SDK/rules boundary](https://firebase.google.com/docs/firestore/security/get-started).

The supplied rule configuration targets the project's default Firestore database and default Firebase Storage bucket. When selecting another database or bucket for production, update the Firebase rule deployment targets to match those resources before deploying.

Metadata lives under `careerOwners/{verifiedUid}`. `workspaces/{id}` stores identifying labels, extraction state, schema version, timestamps and the current immutable description ID. Its `descriptions/{id}` records store content hashes and manifests; `artifacts/{kind}` embeds only Current and Previous version manifests plus a monotonically increasing state token. This bounded document replaces the design's illustrative two-row versions subcollection. Kinds are `job-fit`, `resume`, `cover-letter`, `interview-prep`, and `study-plan`. `notes/interview` is a separate versioned note record. Owner-scoped description indexes atomically deduplicate creation. Creation attempts and generation receipts hold IDs/status/request hashes, never retired artifact bodies. Cleanup records carry only obsolete manifests until deletion succeeds. Workspace pagination uses immutable opaque document ID order and a stable `after` cursor (1–50 records).

Private immutable objects use server-generated `career/{uid}/{workspaceId}/...` paths for descriptions, validated JSON, Markdown, review metadata and PDFs. Manifests bind SHA-256, encoded byte count, MIME and object generation. Reads verify size and hash. Clients select IDs, never paths or remote URLs. JSON, Markdown and review objects are independently capped at 512 KiB; no truncation occurs. Notes are capped at 64 KiB encoded JSON / 100 stable entries. Generation change messages are capped at 2,000 characters / 8,000 bytes. Mail retains its existing 10-file / 10 MiB limits.

`npm run dev` starts Auth, Hosting, Functions, Firestore, and Cloud Storage emulators in `demo-portfolio-local`. The launcher explicitly selects workspace emulators with `JOB_WORKSPACE_EMULATORS=true`, without changing credential files or requiring database/bucket setup. It uses the same server SDK adapters as production against loopback endpoints, the default emulated database and a demo-project bucket. Development temporary files stay under ignored `.firebase/emulator-tmp`; each test suite has a separate temporary root, because Storage deletes its blob directory on shutdown. Emulator data is imported/exported under ignored `.firebase/emulator-data` on clean shutdown/restart. `node scripts/test-firebase-emulator.mjs --model-fixtures` uses isolated ports, synthetic Functions configuration and controlled model output for the same adapters. Client denial is tested against both rules files, including signed-in owners.

Explicit `JOB_WORKSPACE_MODE=emulator` also selects local storage. Both storage endpoints, a demo project and the Functions emulator are required; missing/mixed endpoints fail closed. The launcher flag takes precedence over workspace settings from existing environment files so development never connects to cloud storage. File-backed `JOB_WORKSPACE_MODE=fixture` plus an explicit private `JOB_WORKSPACE_FIXTURE_DIR` remains available only inside the Functions emulator for unit/fault-injection testing. Fixtures are never selected implicitly. Missing live configuration fails with 503 before any model call.

## Requests and recovery

`POST /api/job-workspaces` accepts only `{jobDescription, attemptId}`. Reuse that opaque attempt ID after a lost response. A different posting with the same attempt returns 409. A saved workspace survives extraction or initial-generation failure; unknown metadata remains editable. `GET /api/job-workspaces?limit=20&after=<id>` lists workspaces, and `GET /api/job-workspaces/{id}` retrieves the saved description and independent pairs. `PATCH` accepts `{expectedState, metadata}`; metadata has company/title/location/requisition fields, each string or null. Late extraction cannot overwrite a manual correction.

`POST /api/job-workspaces/{id}/descriptions` accepts `{expectedDescriptionId, jobDescription}`. Earlier descriptions remain readable at `/descriptions/{descriptionId}`. Artifacts retain their source description ID and the UI identifies earlier-posting results. A generation started against an old description cannot promote after a newer description commits.

Generation uses `/artifacts/{kind}/generate` with `{attemptId, mode, expectedState, descriptionId, settings}`. Settings contain tone and weeklyHours; only Revise accepts and requires changeMessage. Initial and Start over include the current posting, approved evidence and current tool prompt with no previous result, old change messages, notes or provider conversation handles. Revise additionally loads Current on the server as untrusted editing context; it never becomes factual evidence. The same tool validators apply in every mode. Provenance records provider/model, prompt/evidence hashes, settings, mode and source description, without credentials or raw evidence dumps.

Files are staged and verified before a transaction publishes the new Current and moves old Current to Previous. Failed generation/storage preserves the pair. A stale state returns 409. Every replacement or undo increments the state token, including swapping back. `/artifacts/{kind}/undo` accepts `{expectedState}` and swaps the same two documents without a model call. First-generation comparison/undo is unavailable. There is no full history or arbitrary restore. The next replacement retires the displaced Previous; its files become inaccessible and cleanup retries deletion. Existing native mail attachment snapshots are independent of these source files.

A stable completed generation attempt returns the same retained version. Once retired, it returns 410 `no_longer_retained`, without regeneration. Active attempts report `in_progress`; after three minutes an unresolved attempt becomes interrupted and requires an explicit new attempt. Provider execution cannot be promised exactly once across a process crash before output persistence. A lost commit acknowledgement is reconciled from the saved receipt before staged content is deleted or a model is invoked again.

Legacy tool endpoints return their original result JSON and add `X-Workspace-Id` / `X-Artifact-Version`. `X-Generation-Attempt` enables reconciliation; omitting it starts a new attempt. Successful tool results always persist. Reopening a workspace alone never regenerates content.

Private notes load/save at `/notes` using `{expectedState, values}`. Stable IDs preserve unmatched notes when generated prompts change. Notes save separately from generated content and never enter model requests, Markdown, PDFs or mail attachments. A stale note save fails visibly; reload before merging another tab's changes.

## Dashboard walkthrough

Open Saved jobs from the dashboard or submit a posting in any tool. Reopening shows saved content and never replaces it automatically. Select an application material independently. Generate creates the first result; Revise requires Requested changes; Start over uses fresh generation context in the same workspace. During requests the saved pair stays available. After replacement, compare the highlighted paragraphs, optionally synchronize native scrolling, and use Undo / Switch back. Mobile uses Current/Previous tabs. The source-posting link exposes an earlier description when needed. A failed request offers Reconcile attempt and Reload saved documents; explicit new generation starts a new attempt.

Use Job details and saved description to correct identifying labels or retain a new posting version. Private interview notes show Unsaved, Saving, Saved, or Save failed. Wait for Saved before leaving; copy failed/stale edits before reloading to merge another tab's changes. Unmatched note prompts remain available after generation.

## PDFs and public release bytes

Résumé and cover-letter saving automatically attempts the matching PDF. Job Fit, Interview Prep and Study Plan require Generate PDF. Each retained version keeps its own not-requested/pending/ready/failed state. Download PDF appears only for a ready source hash; Download Markdown stays independent. Retry PDF never reruns the model. An interrupted pending attempt can be explicitly retried after two minutes. Concurrent attempts are rejected; late output for retired versions is discarded. Downloads authenticate before reading and enforce the PDF 10 MiB limit plus MIME, attachment disposition and integrity checks.

The pinned renderer is `@react-pdf/renderer` 4.9.0 with React 19.2.4. A PDF render from the packaged Functions entry was verified under Node 22.23.1. The renderer is server/build-only. Résumé HTML and PDF share the whitelisted `ResumeDocument` content, approved contact formatting/palette and bundled icon names; print uses separate React PDF primitives, margins and wrapping. Fonts are built-in Helvetica; icons are approved local PNG bytes. Job/model URLs are printed as text and never fetched as PDF resources. Review metadata and personal notes are excluded. No fixed page-count truncation is applied. Explicit line-height styles are avoided because renderer cloning of long documents failed the stress test with those styles.

Every supported public build renders `resume.pdf` only from `publicProfile()`, including every public experience role and bullet plus compact project entries with clickable HTTPS links. The existing résumé email HTML keeps its compact projection. The subtle Download résumé (PDF) link beneath the identity card uses `sitePath` and a named download. A rendering failure fails the build. Firebase packaging copies those same release bytes into `functions/dist/standard-resume.pdf`; the mail fallback reads that file rather than rendering independently. Pages packages the same approved public document under its configured base path. Public allowlists admit only this intentional PDF; private workspace files, fixture data, environment files, interview notes and server bundles remain excluded.

## Application email

In the native composer, open Job application template and choose a workspace. Preview does not mutate the message. Use job application template explicitly replaces subject/plain text/HTML and prepares ready current résumé/cover-letter PDFs; it retains recipients and manual files and never guesses addresses. Missing company/role labels use neutral copy with a correction link. Missing cover letters are disclosed and optional. Pending/failed PDFs require retry in the workspace or an explicit omit choice; Previous is never substituted for Current.

If no tailored résumé exists, choose Use standard résumé or Create tailored résumé. The standard choice attaches the packaged public-release bytes explicitly. Create tailored résumé first seeds useful job-specific copy when blank, flushes serialized native autosave, saves the native draft, and persists owner-bound linkage. Failure retains the composer. Only successful saves navigate to the existing job with an opaque return reference. Return to application email reopens that same native draft after reload/sign-in; Refresh documents can attach the newly ready résumé while preserving recipients, edited copy and manual files. Sending always requires Send message.

`GET /api/job-workspaces/{id}/application-draft` previews availability and copy. POST accepts only attemptId/draftId/content/action (`apply`, `refresh`, `handoff`) and explicit standardResume/omitResume/omitCoverLetter choices. No path/URL/revision selector is accepted. The server authorizes workspace IDs, resolves only ready Current files, verifies source membership while pinning snapshots, validates the combined native 10-file/10-MiB limit, and then updates/verifies the native draft. No send operation occurs. Attempt reconciliation exposes uncertain preparation and avoids duplicate draft creation; retries reuse the same native draft and preparation identity.

`applicationDrafts/{draftId}`, `applicationReturns/{opaqueRef}` and preparation receipts are owner-scoped. Native mail owns saved/sent attachment bytes. Separate private immutable `mail-snapshots` objects retain managed and manual recovery copies with hashes, source version identities and native attachment IDs, allowing refresh after reload without a provider draft-file-download API or source resurrection. These objects are independent of artifact cleanup. Native composer saves update linked recovery manifests when attachments change. An existing unrelated native attachment with unavailable recovery bytes produces an explicit reattachment requirement before replacing files; it is never silently dropped. If native saving succeeds but linkage fails, the composer reports the partial result and retains edits for reconciliation. Reapply changes copy; Refresh changes only managed files. Workspace regeneration/undo/retirement never changes saved or sent mail.

Generation request intent (attempt ID, expected tokens, settings and the owner's change request) is kept in tab-scoped session storage until success or explicit dismissal. Reloading an unfinished/lost-response attempt offers Reconcile instead of automatically starting another model request. Saved artifact content, personal notes and email bodies are not cached there. The server still authorizes and validates the complete request on every retry.

Application return references also survive the login redirect. After sign-in, only the owner role follows the opaque reference; the private return endpoint resolves it within that verified UID before reopening a native draft. This is not an arbitrary return-URL mechanism.

## Download names and tailored sections

PDF/Markdown downloads, tailored HTML, and managed application attachments use candidate-position-company-document-type-year names, for example `james-terrell-singleton-fullstack-developer-clover-resume-2026.pdf`. Labels are lowercase, safely normalized and bounded; unknown job labels are omitted. No workspace/revision IDs appear in filenames. Saved artifact names use their creation year; the public standard link uses candidate-resume-year.

New tailored documents keep their selected roles and skills, add “Previous experience available upon request” when roles are omitted, and show every remaining approved skill in an Additional skills cloud. HTML, plain text/Markdown and PDF use the same supplemental document fields. Older saved documents remain readable; these sections are assembled when generating a new tailored result.

All tools share provider configuration. AI_BASE_URL is needed only for an OpenAI-compatible endpoint; other providers ignore it. A provider connection error is reported as a connection failure without suggesting an unused base URL setting. Credential files are not rewritten to apply this behavior.
